# SOLUTION

## Что сделано

1. **Скидки в `daily-totals`.** Ответ теперь `[{ date, total, gross, discount, net }]`:
   `gross` — сумма `amount` оплаченных заказов, `net` — сумма `amountPaid`, `discount = gross - net`, `total = gross`.
   Всё считается в целых копейках и переводится в рубли в самом конце, поэтому `discount` не накапливает float-ошибку.
   - Миграция `002_discounts.sql`: колонка `amount_paid_kop` (+ `CHECK 0 <= amount_paid_kop <= amount_kop`).
     Уже сохранённые заказы бэкфиллятся значением `amount_kop` (скидки не было).
   - `OrdersService.normalize` принимает `discountPercent` и `amountPaid` (число или строка, поля необязательные).
     Источник правды — `amountPaid`; если его нет, а процент есть — считаем из процента; если нет ничего (заказ из времени до скидок) — без скидки.
2. **Жалоба по `c_7`** — исправлена (см. ниже), плюс ещё два дефекта, найденных по дороге.
3. Тесты на всё новое (деньги, скидки, DST, гонка вебхуков) — в `test/`.

## Причина расхождения по `c_7`

`c_7` живёт в `Europe/Berlin`. Переход на летнее время в 2026 году — **29.03 в 01:00 UTC** (+1 → +2).
`TotalsService.daily` брал смещение зоны один раз — `tzOffsetMinutes(timezone, new Date())`, то есть **на момент запроса**, а не на момент заказа,
и применял его ко всем заказам периода. Сейчас (ноябрь) Берлин в зимнем времени (+1), поэтому все заказы после 29.03 сдвигались на час «назад»:
заказ в 22:40 UTC (по Берлину уже 00:40 следующих суток) попадал в предыдущий день. Именно поэтому 27 и 28.03 (до перехода) совпадали «до копейки», а 29–31.03 — нет.
Баг к тому же зависит от даты запроса: летом тот же код ломал бы дни *до* перехода.

Как нашли: жалоба называет ровно границу «27–31.03» и «часть дней» → подозрение на DST (в конце марта) → в коде единственное место, где время берётся «сейчас».
Подтвердил на реальных данных мока: из оплаченных заказов `c_7` неверный день получают ровно 3 — `2026-03-29T22:40:08Z`, `2026-03-30T22:40:44Z`, `2026-03-31T22:40:06Z`.

Исправление: день заказа определяется форматтером `Intl.DateTimeFormat` в зоне клиента **для момента самого заказа** (`localDateFormatter` в `utils/time.ts`; форматтер создаётся один раз на запрос).

## Что ещё заметил

**В коде**
- **Потеря копейки в `toKop`.** `Math.floor(rub * 100)` на float-шуме: `4723.9 * 100 = 472389.99999999994` → `472389`. В данных мока так ломаются 96 из 3853 значений `amountPaid`
  (`net`/`discount` разошлись бы на копейку). Теперь шум убирается (`Number((rub*100).toFixed(6))`), а настоящие доли копейки по-прежнему отбрасываются — существующий тест `toKop(10.999) = 1099` сохранён.
- **Гонка в `apply`.** `get` → сравнение `updatedAt` → `save` — не атомарно: при параллельной (повторной) доставке вебхуков старая версия может перезаписать новую.
  Теперь проверка «новее» выполняется в самом `INSERT … ON CONFLICT DO UPDATE … WHERE orders.updated_at < excluded.updated_at`; есть тест на параллельную доставку.
- Таймзона клиента кешируется навсегда (без TTL/инвалидации); `tzOffsetMinutes`/`dateAtOffset` теперь не используются в проде (оставил — на них есть тесты).
- Невалидный вебхук отвечает 400 — отправитель, скорее всего, будет ретраить его бесконечно; вебхуки без аутентификации/подписи.
- `POST /sync` синхронный: ~52 страницы при ≤4 rps — это десятки секунд в одном HTTP-запросе.

**Во внешнем API** (по полной выгрузке: 5030 заказов, 40 клиентов, 52 страницы)
- `discountPercent`/`amountPaid` есть только у заказов с 2026-03-15 (с `o_01164`); у 1177 более ранних — нет совсем.
- `discountPercent` у 177 заказов приходит строкой (`"13"`), `amount` у 157 — строкой (`"3100.00"`).
- `createdAt` без указания зоны у 288 заказов (`updatedAt` всегда с `Z`).
- `amountPaid` заполнен и у `pending`/`refunded` (1440 заказов) — то есть это «сколько было бы/было оплачено», а не признак оплаты; учитываем только `paid`.
- `amountPaid` везде равен `amount * (1 - discountPercent/100)` с точностью до копейки (расхождений 0 из 3853) — данные согласованы.
- Конец выдачи: пустая страница с тем же `nextCursor` (уже обработано в `sync`).
- Вебхуки: 92 события по 21 заказу (все `c_7`), каждое доставляется 2–6 раз, версии приходят не по порядку (например, `refunded` раньше более старого `paid`). Применилось 26, устаревшими признано 66.

## Допущения

- Дата заказа — по `createdAt` (как в существующей логике), а не по моменту оплаты/`updatedAt`. Считаются заказы, которые **сейчас** в статусе `paid`; `refunded` исключается целиком (частичных возвратов в данных нет).
- `createdAt` без зоны — UTC (как заявлено в контракте и в существующем `parseUtc`). Косвенное подтверждение по данным: медиана `updatedAt − createdAt` у таких заказов 304 мин против 300 у заказов с `Z`.
- Заказ без `amountPaid` и без `discountPercent` — без скидки (`net = gross`). Если `amountPaid > amount` — заказ считается невалидным (попадёт в `invalid` при синке / 400 в вебхуке), т. к. скидка получилась бы отрицательной.
- Доли копейки отбрасываются (как и раньше); в данных их нет.
- **Ответ `daily-totals` расширен**, поэтому три существующих проверки `toEqual` в `test/totals.test.ts` дополнены новыми полями (`gross/discount/net`). Другой способ добавить поля, не меняя эти ожидания, невозможен; остальные тесты не менялись.

## Как проверял

- Логика денег, времени, нормализации заказов и агрегации (реальный код `OrdersService`/`TotalsService`) прогнана на **полной выгрузке мок-API** (5030 заказов) + 92 вебхука — с in-memory репозиторием вместо PostgreSQL, с той же семантикой «записываем, только если `updatedAt` новее».
- Результат сверен с **независимым расчётом** (отдельный скрипт: свежайшая версия заказа по `updatedAt`, день через `Intl` в `Europe/Berlin`, суммы разбором десятичных строк без float) — совпадение полное.
  Для сравнения: на старом коде `gross` за 29–31.03 расходится с верным значением, а 27 и 28.03 совпадают — ровно как в жалобе.
- Границы DST проверены тестами: 01:00 UTC 29.03 для Берлина и 07:00 UTC 08.03 для Нью-Йорка; тест на Берлин падает независимо от того, зимой или летом он запущен.
